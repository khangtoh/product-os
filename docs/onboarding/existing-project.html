Onboarding / Existing project

Bring an existing project into ProductOS.

Adopt ProductOS around the contracts, code, evidence, and work your team already has. Preserve history and fill the gaps that matter.

Existing app or productReuse established contextPreserve ongoing work
01 / Establish the target

Start with the product's current truth.

Identify the product or app being onboarded, its actual project root, the owner of product direction, and any current ProductOS instance. In a monorepo, do not assume every app shares one vision or product contract.

Work from the project's normal branch and review process. Check the current working tree and preserve unrelated changes before adding context. Existing instructions still govern inspection and edits.

Bring the sources that already guide the team
SourceWhat it can establish
Product contracts, briefs, PRDs, and requirementsEstablished intent, desired behavior, constraints, and links to maintained specifications.
Code, tests, and release artifactsImplemented behavior and verified checks. Code alone does not prove demand or improved outcomes.
Roadmaps, issues, and ongoing workCurrent commitments, owners, dependencies, and competing priority signals.
User research, support notes, and analyticsObserved problems or results, with provenance, dates, access limits, and measurement caveats.
Operational and design guidanceActual platforms, service context, permission boundaries, accessibility requirements, and design conventions.
Existing ProductOS recordsStable IDs, lifecycle conventions, decisions, learning, and any unfinished onboarding checkpoint.

The adoption rule: reuse reliable answers, link maintained sources, and interview only for missing or conflicting information. Preserve project facts, local adaptations, IDs, history, and existing operating scope.

Choose setup, resume, or orientation

Use init when adopting ProductOS or completing its brief; resume when an unfinished onboarding checkpoint exists; and orient when a contributor is joining an initialized product. Orientation explains established context and does not reset ownership, priorities, or the interview.

02 / Install without replacing context

Keep the framework separate from your product.

Obtain the framework checkout outside your target project, if you do not already have it. From that checkout, run:

python3 scripts/install_skill.py --project /absolute/path/to/your-project --agent codex

Replace the target path with your existing project directory. Select --agent claude for Claude Code or --agent both for both harnesses. The installer uses Python 3's standard library, requires no network access, and installs the skill plus bundled templates. It does not initialize product context.

The installer refuses an existing skill destination and symlinked skill directories. Preserve local edits and use the skill update guidance when the skill already exists. Updating a skill is separate from changing or migrating product records.

Open the target project in the agent

$product-os init

In Claude Code, use /product-os init. These invocations belong in the agent conversation, not the terminal. Start a new session if the skill is not listed.

Give the agent the scope and preservation intent:

Onboard this existing project to ProductOS.
Inspect the current product contract, requirements, roadmap, evidence,
and ongoing work first. Reuse reliable answers and preserve history.
Keep each fact in its authoritative home and link existing specifications.
Ask me only about material gaps or conflicts, then save the brief and handoff.
Do not start implementation as part of onboarding.
Adopt without the installer or with another agent

Use the portable prompt workflow. If no product folder exists, copy only template/product/ into the target as product/. If a folder already exists, inspect it and merge only missing, relevant documents. Do not run a blanket copy over applied records or an unrelated directory.

Open the target project and ask:

Read product/ONBOARDING.md and guide adoption into this existing project.
Inspect and preserve the current product context, reuse established facts,
resolve material gaps with me, and save a checkpoint between interview rounds.

If an older instance lacks ONBOARDING.md, use the bundled guide or the source template's procedure while preserving the local model. If product/ has an unrelated meaning, agree on a suitable context location before writing and adapt all references. See the quickstart for manual skill installation without Python.

03 / Reconcile what is known

Make gaps and conflicting signals explicit.

The agent should summarize what the repository establishes and what remains uncertain before asking questions. Use small rounds of two or three related questions. Save supported answers in the canonical files and coverage links, remaining questions, and next topic in STATE after each answered round.

Questions that matter for an existing project
AreaResolve only what remains open
Intent and audienceDoes the current contract still represent owner direction? Which users and problems have evidence, and which remain hypotheses?
Workflows and requirementsWhich user tasks matter now? Which behaviors are implemented, unverified, or missing? Where are acceptance criteria maintained?
Constraints and operationsWhat must remain intact? What platforms and tools actually exist? Which operating permissions and access limits already apply?
Success and evidenceHow is the intended outcome measured? Are definitions and sources trustworthy? Which baselines or observations are unavailable?
Priorities and starting pointWhich priorities are current? What work is already underway, who owns it, and what dependency determines its next action?
Contract completenessWhich required contract fields are missing, including name, promise, Register, users, purpose, platform, boundaries, and navigation?

For example, a roadmap may prioritize acquisition while current owner direction prioritizes retention. Show the competing sources and ask the owner to resolve that material conflict; do not silently choose by document length or recency alone. A user complaint can be evidence without becoming permission to change product direction.

Fictional example / PocketGarden

Preserve behavior while documenting what is missing.

The prototype already saves article links, searches titles, and opens originals. Its requirements say an empty search should explain the result and allow another query. Inspection shows that message is missing; it does not establish whether users can successfully retrieve old articles.

Record the implementation gap, preserve the owner's protected saving flow, and keep the outcome baseline unknown until observations exist. The demo has a proposed observation metric, not measured results. See demo requirements and the proposed metric.

When a decision is deferred, preserve the question, consequence, owner if known, next discovery action, and whether it blocks work. A proposed solution becomes selected direction only after the owner's answer. Save conflicting evidence rather than rewriting history to make every source agree.

04 / Merge the product memory

Preserve the authoritative contract.

Preserve existing record IDs and historical decisions. Local model adaptations continue to govern existing records; adoption does not authorize schema migrations or renumbering. Follow the canonical model for new records where it applies.

Connect future sessions

Merge a context pointer into the existing root agent instructions, preserving unrelated content and avoiding duplicates. Adapt these paths when the contract or context lives elsewhere:

## Product context

For product work, read PRODUCT.md, product/AGENTS.md, and product/STATE.md
before making changes. Follow linked vision, requirements, roadmap, and
work records as needed. Update the affected context after material
product decisions or results.

Use the harness's equivalent agent configuration where applicable. A nested AGENTS.md alone may not be read during work elsewhere in the repository. Report exactly which instructions and context documents changed.

What setup provides today

Guided interviewing, Markdown product memory, saved checkpoints, orientation, and a procedure for one bounded action are available. The installer currently uses Python; the documentation model itself needs no runtime.

Dedicated journey records and validation, a TypeScript CLI, DuckDB metrics collection, an HTML metrics dashboard, an MCP client, committed .product-os/ events, and automatic artifact migrations are planned. This guide does not install or activate them. See the metrics and experiments plan and event logging requirements.

05 / Verify adoption

Review the diff and the handoff.

  • The correct product is identified, with one authoritative home for each fact.
  • Original contracts, specifications, IDs, history, and local adaptations remain available; unrelated changes are preserved.
  • All eight required brief areas are addressed through reliable sources, owner direction, selected hypotheses, or explicit deferrals.
  • Implemented behavior, unverified claims, owner requirements, proposals, and user evidence are distinguishable.
  • Roadmap and STATE reflect actual priorities and ongoing work, with owners, blockers, and the next action.
  • Existing metric definitions and historical results are preserved. Missing observations are unavailable or unknown, never fabricated zeroes.
  • Relative links and agent pointers resolve from the actual contract locations.
  • The owner has received a linked summary, a list of material changes, unresolved decisions, and an opportunity to correct misunderstandings.

Review the documentation changes through the project's normal Git process. Setup does not mark existing outcomes achieved or work complete. An initial brief can be complete while a proposed action remains blocked by access, scope, ownership, or success criteria.

If the project is read-only: the agent should show proposed edits and the unsaved checkpoint, then identify what could not be saved. It must not report completed setup or saved context. A future writable session can apply the proposal and resume.

06 / Resume useful work

Continue from the current state.

An onboarding-only request ends with the saved summary and proposed next action. When you want execution, use $product-os run or /product-os run. The agent should inspect current reality, resume eligible ongoing work before selecting new work, verify within established scope, and save a handoff.

Use these inside the target project's agent session
IntentCodexClaude Code
Set up or finish the brief$product-os init/product-os init
Continue an unfinished interview$product-os resume/product-os resume
Introduce a contributor to saved context$product-os orient/product-os orient
Carry out the next bounded product action$product-os run/product-os run

Recover an interrupted adoption

$product-os resume

In Claude Code, use /product-os resume. Continue from STATE's saved coverage and next unresolved topic; do not repeat settled questions. Use orient for a new contributor, rather than restarting the adoption interview.

For recurring work, see automation. The current skill installs no continuous runner or registered schedule. Product documents and skill updates do not expand release, spending, tool, or service authority.
