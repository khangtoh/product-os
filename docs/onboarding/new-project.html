Onboarding / New project

Start a new project with ProductOS.

Turn an idea into a saved product brief, clear requirements, and a first learning goal that a human or agent can continue.

Empty folder or early ideaGuided conversationSaved product memory
01 / Prepare

Start with the problem you want to understand.

You can begin with an empty folder, an idea, and access to an agent. Bring any notes you have about the people you want to help, their current alternatives, and the outcome you hope to change. Early assumptions are welcome when they are labeled as hypotheses.

Bring direction

A product owner, an initial audience hypothesis, the essential user task, known constraints, and the question you want to answer first.

Leave room to learn

You do not need a finished specification, validated demand, telemetry, a numerical target, a release date, or a full backlog to start.

Choose one product as the target. Keep its directory outside the ProductOS framework checkout. In a monorepo, establish which app and product contract this onboarding concerns.

02 / Set up the entry point

Give your agent the method.

For a new project, run the following from the directory that will contain both the project and the framework checkout. Change my-project to your chosen name. If the project directory or checkout already exists, reuse it and skip its creation command.

mkdir my-project
git -C my-project init
git clone https://github.com/khangtoh/product-os.git
cd product-os
python3 scripts/install_skill.py --project ../my-project --agent codex

The installer needs Python 3 and uses only its standard library. Git initialization is optional for drafting, but gives your product documents version history. The clone needs repository access. The installer itself works offline.

Choose the installer flag for your harness: --agent codex (default), --agent claude, or --agent both. It installs the entrypoint and bundled blank templates into the target's agent skill directory. It creates no product brief and runs no product work. If a skill destination exists, preserve local changes and follow the skill update instructions; the installer refuses to overwrite it.

Open the target project and start onboarding

Open my-project in Codex or Claude Code, rather than continuing inside the framework checkout. Start a new agent session if the skill is not listed.

$product-os init

In Claude Code, use /product-os init. These are agent skill invocations, not terminal commands.

Use another agent or follow the documents manually

Copy only template/product/ from the framework checkout to the target's product/ directory. Preserve any existing destination; the quickstart provides a guarded copy command. Do not copy the framework's maintenance instructions or fictional demo records into your product.

Open the target project and give the agent this prompt:

Read product/ONBOARDING.md and guide me through ProductOS onboarding.
This is a new project. Help me define its purpose, users, essential workflows,
requirements, boundaries, success criteria, and initial priorities.
Save supported answers and a resumable checkpoint as we go.

A human can follow the same procedure. No hosted service or agent runtime is required for the documentation model. Manual skill installation for Codex and Claude Code is also covered in the quickstart.

03 / Define the brief

Work through a few questions at a time.

The agent inspects the project first, then asks two or three related questions per round. Answers are saved in their canonical documents after each round, with remaining questions and the next topic in product/STATE.md.

What the conversation should establish
TopicQuestions to answer
Purpose and peopleWhat lasting change should the product enable? Who needs it, in what situation, and what do they use today? What is the product's name and promise?
Core experienceWalk through the essential task: actor, trigger, important steps, intended result, and relevant failure or recovery paths.
Initial requirementsWhat must the first version do? What observable check would show each required behavior works? Which quality and accessibility requirements matter?
BoundariesWhat is out of scope? What must remain intact? Which platform, resource limits, operating constraints, and tradeoffs apply?
SuccessWhat user outcome matters? How could you observe it? What evidence exists, what is still a hypothesis, and which measurements are unavailable?
Direction and starting pointWhich outcomes belong Now, Next, and Later, and why? Who owns the first action? Which unresolved decisions block it?

Resolve the product-wide Register with the owner: brand or product. The agent should explain the choice when it is unclear. Detailed visual styling belongs in design guidance.

If you do not know yet: ask for options and tradeoffs. Choose a working hypothesis or explicitly defer the decision. A useful deferral records the question, its consequence, an owner if known, and a discovery action. Mark whether it blocks the next action. An unanswered question stays unanswered.

Fictional example / PocketGarden

Make a workflow concrete.

A researcher saves an article while reading, later searches the collection by title, and opens the original URL. If nothing matches, the interface explains that and allows a revised query.

Possible first learning goal: understand whether researchers can find and open articles they saved weeks earlier without help. Before observations exist, the baseline is unknown. A built search feature alone does not establish successful retrieval.

This illustrates workflow documentation in REQUIREMENTS.md; it is not a dedicated journey-schema record. See the captured demo workflows and demo outcome.

Pause and resume

Ask the agent to save the current answers, remaining questions, and next interview topic. In a later target-project session, use $product-os resume or /product-os resume. If no checkpoint was saved, the agent should say so and offer init. Missing answers keep setup incomplete.

04 / Review the saved documents

One home for each product fact.

For the default new-project layout, onboarding creates a root PRODUCT.md and supporting context under product/. Its local PRODUCT.md becomes a navigation pointer. If the product-context folder is itself the repository root, keep its contract there.

Where onboarding saves the answers
LocationWhat belongs here
PRODUCT.mdThe canonical product contract: identity, users, purpose, boundaries, and navigation. New projects normally place it at the root.
product/PRODUCT.mdFor the default new layout, a pointer to the root contract, current state, and roadmap. An established local contract can remain canonical.
product/VISION.mdLasting ambition and durable principles.
product/REQUIREMENTS.mdCore workflows, functional and quality requirements, acceptance criteria, exclusions, and open decisions. Link existing specifications where they are maintained.
product/STRATEGY.mdCurrent approach, rationale, assumptions, and what would change the approach.
product/ROADMAP.mdNow / Next / Later outcome priorities and their rationale.
product/STATE.mdInterview coverage and checkpoint, current work, owner, blockers, and the next action.
product/METRICS.mdMeasurement definitions when established; unknown baselines remain unknown.
product/operations/Verified operating context, existing scope, access gaps, and relevant systems.
Root agent instructionsA product-context pointer merged into existing instructions, with paths adapted to the actual layout.

The contract should have the product-name H1, promise, required canonical headings, and open PRODUCT.md metadata from the template. Register must agree between the section and frontmatter; promoted links must point to the actual supporting files. See the contract guide for the complete rules.

Keep early records small. Create outcome or work records only when useful, using the existing model and templates. A new roadmap can have one meaningful Now outcome and empty Next or Later horizons where no priority has been established. Setup does not activate work automatically.

What setup provides today

Guided interviewing, Markdown product memory, saved checkpoints, orientation, and a procedure for one bounded action are available. The installer currently uses Python; the documentation model itself needs no runtime.

Dedicated journey records and validation, a TypeScript CLI, DuckDB metrics collection, an HTML metrics dashboard, an MCP client, committed .product-os/ events, and automatic artifact migrations are planned. This guide does not install or activate them. See the metrics and experiments plan and event logging requirements.

05 / Check completion

A complete brief should let someone continue.

  • All eight required brief areas have supported answers, owner direction, selected hypotheses, or explicit owner deferrals.
  • Workflows include relevant failures and observable acceptance criteria.
  • Sources, uncertainty, measurement gaps, and deferred decisions are visible.
  • The saved contract, roadmap, requirements, and STATE agree.
  • Links resolve and root agent instructions point to the actual product context.
  • The first proposed action has an owner, a clear purpose, and visible readiness dependencies.
  • The owner has been shown a linked summary and can correct misunderstandings.

A field containing only unknown does not show that a required topic was discussed. A complete brief can still require discovery before implementation; STATE should explain that dependency.

Save the onboarding documents in your project's normal Git review process. Review the diff for accidental unrelated edits, secrets, and unsourced claims. Completion follows the existing model and does not require an extra approval round for answers already given.

06 / Begin the first useful loop

Separate setup from doing the work.

An onboarding-only request ends with a summary and the proposed first action. When you want that action performed, invoke $product-os run or /product-os run, or use:

Read the product context and current state. Carry out the next eligible
bounded action using product/EXECUTION.md, verify the result, and save a handoff.

The next action might be a user interview, a prototype, a verification task, or an implementation step. It follows established scope and tools. ProductOS records what happened, what was observed, and how the work resumes. A release and a validated product outcome remain separate claims.

Use these inside the target project's agent session
IntentCodexClaude Code
Set up or finish the brief$product-os init/product-os init
Continue an unfinished interview$product-os resume/product-os resume
Introduce a contributor to saved context$product-os orient/product-os orient
Carry out the next bounded product action$product-os run/product-os run

A proposed review date in a file is not a registered schedule. Recurring execution needs an actual runner, working tools, and appropriate authority; see automation.
